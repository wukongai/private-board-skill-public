# 会议文档交付

## 一份主文档
会议成果默认按templates/decision-memo.md组织为一份面向案主的Markdown主文档，包含会议纪要、决议与待决事项、执行方案、下次会议议题。既有项目规范要求拆分时可拆分，但给唯一主入口和链接；不另造与产品定义冲突的事实源。
会议纪要记问题演变、材料依据、真实案主选择和不同幕僚判断，不代写逐字记录或未发生发言。决议分已确认、建议待确认、暂缓/否决；执行方案写首步、产物、范围、验收、负责人/时间或待约定。未解项不伪装决议。

后台session模板与阅读版成果分开保存：题库映射、指纹、内部ID只进后台恢复记录，不以“恢复附记”“附录”或折叠块混入阅读版。需要后台文件时按调用方路由单独存放；未保存后台信息也不能拿阅读版充当后台。

## 开场确定落点
先读调用方项目的文档路由/AGENTS，复用已指定的会议记录；没有规范时在当前项目docs/meetings中按日期和议题拟定唯一文件名，重名增加序号。缺项目目录则问一个保存位置问题，不猜其他项目。记录放案主项目，不放Skill源码目录。
复用已有保存授权；用户明确要求“保存、落地文档、形成会议文件”已授权此记录，无需重复确认。未授权时先说明拟存位置，仅问一次是否保存；不能将讨论同意当文件授权。案主只要聊天则提供完整可复制成果，明确未生成文件。
已授权且能写文件时，在发出开场第一问之前建立含会议约定的草稿。此后每次准备回复时，对照上次已保存状态：本轮出现新的阶段判断、真实决议、责任/行动/停损变化、预算更新或偏题停放，就先将实际变化增量写入，再发小结与下一问。普通业务轮同样适用；不等第6轮或结会才补记，也不需要每轮重写整篇逐字稿。
增量保存不是只在末尾追加：主文档与后台各自只保留一处明确的当前状态区；同时更新当前轮数/预算、讨论状态、最新决议与行动总述、下一步、最后已处理/保存轮次及待存原因。已被新决定替代的“尚待决定”“上次保存0轮”等当前字段必须替换，不能与新状态并列；旧值如有保留必要，移入明确标注轮次的历史记录。
每次回读同时核对当前状态区、决议/执行方案总述与本轮新增段，确认不存在相互矛盾的活动摘要；后台也核对最后回答、下一问和最近保存字段。不要仅因末尾出现新决定便认为同步完成。下一回复前若有前次待存，先补存；没有内容变化不重复写。
工具返回成功后读取实际变更段和顶部，确认与本轮决定相符；读取失败或写入失败则保留待存事件与原因，聊天明确尚未同步，不伪称已更新。权限失败不停止有意义讨论，亦不增加业务问题来拖延交付。

## 结构化保存入口
宿主可运行Python时，已授权的本场记录使用Skill内scripts/meeting_record.py写入，不手工拼接或复制旧会议全文。这是记录工具，不替代主持的商业判断、案主确认或保存授权。
每次读取最新实际记录，生成完整当前快照JSON，字段如下（全部必填；列表可空）：
- round、budget：真实累计实质答复及已批准总预算；status：in_progress / closed / conditional / paused。
- goal、summary：本场目标、最新判断与继续/结束理由，不重复历史状态。
- decisions、open_items、parked：当前决议、仍未决/取证、暂缓及下一场，均为文字列表；已解决项从open_items移出。
- actions：每项含owner（责任/权限）、step（首步与产物）、when（完成窗口）、stop（验收/停损信号及触发处置）；未知如实写未确认，不编批准。
- event：本轮真实发生的资料、交叉判断与案主决定，组成阅读版历史纪要；只记增量，不放后台编号，不把旧待决重写成当前。
- backend_notes：本轮后台证据映射/依据；只在后台与历史事件中出现。
预算改变时另提供budget_approval，摘录真实案主许可；不能为了让工具通过编造同意。工具只能检查该记录存在，主持仍须核实来源。

运行：python3 -B <本Skill目录>/scripts/meeting_record.py --input <本轮快照.json> --meeting <已授权目录/meeting.md> --backend <同目录/host-record.md>。
工具生成唯一当前状态、决议和执行方案，旧快照自动归档为历史，保存前备份旧版，对本工具写入加单写者锁，并在提交前再次检查可见外部修改，读回内容一致才返回成功。锁仅协调本工具实例，不是任意编辑器的跨文件事务锁；同步期间避免其他编辑器同时改同一记录。遇外部修改先保留双方并合并；现有非工具管理文档不直接覆盖，可在获准路径创建新记录并引用旧稿。后台和阅读版应在同一已授权目录；运行输入、隐藏状态和历史也留在该会议目录，不写回Skill源码。
主持收到成功后仍检查当前决议/未决是否与真实回答相符，工具不能自动判定商业完成或承诺是否充分。工具不可用时按前述协议手工保存并说明未使用结构校验；任何失败保留待存状态，不称工具已核验。

## 结会保存与核验
按顺序：按convergence.md核对关键责任/执行步骤/停损确认→判定完整或条件收束→完成成果主文档→写入→重新读取核验→在聊天给摘要与实际文件链接。核对未通过时不能先宣布完整结会再把可当场确认的内部决定列为外证。用户结束或预算到限仍交付条件成果。
已有文件先读再改，保存前比对上次读取内容；有外部修改则合并，不覆盖。修改已有会议成果前保留版本备份；同场恢复继续该主文档，新场另建并引用上场。使用稳定会话标识防重复创建。
回读确认对象、预算和结束原因、纪要、决议/待决、执行方案、下次议题均存在且与真实对话一致。不能用“命令成功”代替内容核验，不编时间/负责人/批准。阅读版正文不展示后台会话标识、消息指纹或内部清单编号；保存内容不包含凭证或无关个人隐私。
回读时同时检查展示：阅读版（含所有附录）不得残留题库编号、指纹和后台恢复字段；顶部当前状态须更新为实际预算与结会/待保存状态，开场旧状态仅在明确标为历史的纪要中保留。发现残留先移至后台、修正文档并再次回读；不得在检查未通过时声称成果已核验。
只有真实写入且回读通过，才称“会议成果已落盘”，提供实际路径。文件已保存不等于建议获批准或执行已完成。不会自动写代码、改产品定义、创建任务、发消息或新会话；这些按明确授权另行处理。

## 失败与完成状态
讨论状态和文档状态分开：会议可已结束，文档仍待保存。路径未知/无授权/无写能力/写入失败/回读不符，明确具体限制并给完整可复制成果；保持“讨论已收束，文档待落盘”，不得继续追问业务来填补保存失败。
恢复优先补存同一成果并核验，不重开问卷。若案主明确选择仅聊天，则尊重选择，标“仅聊天交付，未写文件”，不虚称落盘。
